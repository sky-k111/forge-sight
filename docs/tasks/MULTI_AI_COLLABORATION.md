# 多 AI 开发分工与交付协议

> 状态：协作基线
>
> 适用范围：Q、M、R、V、N、E、U、T 全部项目任务
>
> 核心原则：推理密集工作交给推理 AI，视觉与体验工作交给 Codex；
> 任何共享文件都通过前置 PR 合并后再修改，不允许双方在两个未合并分支中同时编辑。

## 1. 角色定义

### 推理 AI

负责领域建模、状态机、数据库迁移、Agent 编排、权限、安全、幂等、
并发、重试、容量和后端测试。

优势使用方向：

- 推导状态和不变量。
- 识别并发、事务、重放、权限和数据一致性问题。
- 设计稳定 API、事件和数据库契约。
- 编写后端服务、迁移及自动化测试。

### Codex

负责产品体验、界面、精美排版、图片、图表、PDF 视觉、邮件视觉模板、
响应式与可访问性、浏览器测试、跨任务集成，以及所有提交的最终审查。

Codex 也是最终质量门负责人：推理 AI 的 PR 未经 Codex 审查不得合并。

## 3. 推理 AI 的明确工作清单

将本文件交给推理 AI 时，同时指定一个大任务或一组连续小任务。推理 AI 必须：

1. 先阅读 `AGENTS.md`、`docs/tasks/REQUIREMENTS.md`、对应的 `字母00`，
   以及本任务下所有指定小任务文件。
2. 从最新 `main` 建立独立分支，每个大任务单独 PR，不建立跨任务巨型分支。
3. 测试先行：先提交或展示预期失败的测试，再写最小实现使其通过。
4. 对 schema、API、事件、错误码和环境变量写出稳定契约。
5. 数据库变更必须增量、幂等，不得删除存量用户、报告、会话或审计数据。
6. 所有外部副作用使用可替换接口；测试使用 fake provider，不调用真实邮箱。
7. 提供单元测试、集成测试、并发/幂等测试和必要的安全负例。
8. 开 Draft PR，不自行合并；CI 通过后才标记 Ready for review。
9. 在 PR 中请求 Codex 最终审查，并等待审查结论。

## 4. 推理 AI 不得做的事情

以下内容由 Codex 独占，推理 AI 不得修改：

- `frontend-new/**`
- 页面颜色、字体、间距、布局、图标、动效和响应式规则
- PDF 的 HTML/CSS、分页视觉、封面、图片、图表和表格样式
- 邮件 HTML/CSS 视觉模板及邮件截图
- 浏览器视觉测试、截图基线和可访问性视觉修复
- `.github/**`、`CODEOWNERS` 和 CI 工作流
- 根 `README.md`
- `docs/tasks/**` 中的任务状态和目录迁移

推理 AI 同样不得：

- 直接推送或合并到 `main`。
- 使用 `force push` 覆盖他人提交。
- 提交真实 API Key、邮箱密码、授权码、SMTP 密钥或用户邮箱数据。
- 为了让测试通过而关闭鉴权、跳过校验或硬编码验证码。
- 把自动发布重新改成人工审批主链路。
- 在未提出契约变更说明的情况下改变已冻结字段、状态或错误码。
- 顺手重构任务以外的模块。

## 5. 文件所有权与防冲突规则

### 推理 AI 可直接修改

- `backend/app/auth/**`
- `backend/app/db/**`
- `backend/app/agent/**`
- `backend/app/api/**` 中指定任务的路由
- `backend/app/reports/**` 中非视觉渲染部分
- 后端邮件 Provider、队列、Worker 和投递服务
- `backend/tests/**`
- `database/**`
- 与任务直接相关的 `.env.example` 和后端配置项

### Codex 保留路径

- `frontend-new/**`
- `backend/app/reports/rendering/**`：PDF 视觉渲染
- `backend/app/mail/templates/**`：邮件 HTML 与纯文本模板
- `docs/acceptance/visual/**`：视觉验收证据
- `.github/**`：仅在用户确认 CI 方案后由 Codex 实施

### 共享文件

以下文件只能串行修改，不允许双方并发：

- `backend/app/db/models.py`
- `backend/app/config.py`
- `backend/app/main.py`
- `backend/app/api/reports.py`
- `backend/app/reports/service.py`

规则：推理 AI 的基础 PR 先合并；Codex 再从更新后的 `main` 建视觉或集成分支。
如果确实必须修改共享文件，PR 描述必须列出文件和原因。

## 6. 契约冻结与变更流程

每个后端任务在实现前先提供以下内容：

- 请求和响应示例。
- 状态枚举及合法转换。
- 业务错误码和 HTTP 状态码。
- 数据权限和接收人范围。
- 事件名称、幂等键和 payload。
- 数据库唯一约束与索引。

Codex 审查通过后标记为“契约冻结”。冻结后如需调整：

1. 单独列出旧契约、新契约和变更原因。
2. 说明对前端、PDF、邮件、迁移和已有数据的影响。
3. 未经 Codex 确认不得直接修改实现。

## 7. 推荐实施顺序

```text
批次 A
Q 后端 → Codex 审查 → 合并
M 后端 → Codex 审查 → 合并

批次 B
R 后端 ┐
V 核心 ├→ 分别审查并合并
N 后端 ┘

批次 C
E 核心 → 审查并合并

批次 D
Codex：V05 + E02 + U01～U09
推理 AI：T01/T02/T04/T05/T06/T08/T09

批次 E
Codex：T03 + T07 + T10 + 全量最终审查
```

即使批次 B 可并行，也必须各自使用独立分支和 PR。V05 必须从 V 核心合并后的
`main` 创建，E02 必须从 E01 合并后的 `main` 创建。

## 8. 推理 AI 每次交付必须提供

PR 描述必须包含：

- 本次完成的任务编号，例如 `M01～M04`。
- 实际修改文件清单。
- schema、API、事件和环境变量变化。
- 数据迁移、回滚及存量数据兼容说明。
- 测试命令及完整结果。
- 并发、权限、幂等和安全风险。
- 尚未完成的内容和明确后续任务。

不得用“测试应该通过”“逻辑看起来没问题”代替真实命令输出。

## 9. Codex 最终审查门

Codex 对每个推理 AI PR 至少检查：

1. 是否严格处于分配范围内。
2. 是否破坏冻结契约或已有 API。
3. 迁移是否幂等、可在存量平台库执行。
4. 权限、邮箱隐私、验证码、下载链接和日志是否泄密。
5. 事务、Outbox、重试和幂等键是否覆盖失败场景。
6. 单元、集成、并发和回归测试是否真实通过。
7. 是否给 U、V05、E02 留出稳定且不含视觉决策的数据接口。
8. 是否存在无关重构、重复代码或隐藏技术债。

审查结果按 `Critical / Important / Minor` 输出。Critical 和 Important 清零后，
才能合并；合并后由 Codex 更新任务状态。


## 11. CI 讨论边界

GitHub CI 方案仍处于讨论状态。在用户明确确认前，任何 AI 都不得创建或修改：

- `.github/workflows/**`
- `.github/CODEOWNERS`
- GitHub Ruleset 或分支保护配置
- 自动合并、自动发布或自动部署配置
