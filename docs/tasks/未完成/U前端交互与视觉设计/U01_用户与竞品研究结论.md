# U01 用户与竞品研究结论

> 状态：待产品确认
>
> 研究日期：2026-08-13
>
> 平台：Web

## 一、问题定义

ForgeSight 不是通用 BI 看板，也不是聊天工具。它需要把 Agent 自动生成的周报、管理员
公告、邮件投递状态和可追溯证据组织成一个可信的制造业经营工作台。

当前用户遇到的核心问题不是“缺少更多图表”，而是：

- 管理者需要在一分钟内知道本周是否偏离目标、最严重的问题是什么、谁应当行动；
- 业务人员需要确认结论来自哪个周期、指标口径和数据范围，并能继续查看证据；
- 管理员需要发布公告、确认接收范围、定位投递失败，但不能看到不必要的敏感信息；
- 移动端用户通常从邮件或消息链接临时进入，只需要先看结论、异常和行动，不适合直接
  缩小桌面三栏页面。

因此，U 任务的设计目标是“先给结论，再给比较，最后给证据”，同时保持报告、消息和
邮件之间的状态一致。

## 二、用户与使用场景

### 1. 桌面端管理者

- 环境：会议前、经营例会或办公室桌面，常用 1280～1440px 屏幕。
- 首要目标：判断是否需要介入，并快速找到最严重异常和责任动作。
- 首屏寻找顺序：报告周期与范围 → 总体结论 → 关键指标变化 → 严重异常 → 行动建议。
- 可接受行为：继续展开图表、明细和证据；下载 PDF 用于存档或会议。
- 不可接受行为：先阅读技术流程、章节任务和 SQL，或在多个同权重卡片中寻找结论。

### 2. 桌面端业务人员

- 环境：日常分析与问题跟进，需要在页面和数据证据之间往返。
- 首要目标：理解变化原因、核对口径和数据质量、执行行动项。
- 首屏寻找顺序：异常与趋势 → 分组贡献 → 数据质量 → 证据入口。
- 可接受行为：使用筛选、查看表格、下载 Excel、进入分析证据链。
- 不可接受行为：仅有结论而没有比较周期、单位、来源或异常明细。

### 3. 移动端临时阅读者

- 环境：从邮件或站内消息进入，375px 左右，单手短时阅读。
- 首要目标：在 30 秒内确认是否紧急、是否与自己相关、下一步是什么。
- 首屏寻找顺序：标题与周期 → 一句话结论 → 最严重异常 → 行动 → PDF 下载。
- 可接受行为：纵向阅读简化图表，横向滚动查看必要表格。
- 不可接受行为：缩放桌面图表、依赖悬停、在三栏布局中定位内容。

### 4. 系统管理员

- 环境：桌面管理台，关注公告发布和邮件失败定位。
- 首要目标：明确谁会收到公告、失败发生在哪一环、是否适合重发。
- 操作顺序：筛选 → 查看影响范围或失败原因 → 执行发布/撤回/重发 → 获得明确结果。
- 不可接受行为：完整邮箱暴露、模糊错误、重复创建业务投递、业务用户看到管理入口。

## 三、关键任务与成功标准

| 任务 | 用户需要回答的问题 | 页面成功标准 |
| --- | --- | --- |
| 邮箱门禁 | 为什么进不去，下一步做什么？ | 两步内发送验证码，支持粘贴和重发，错误可恢复 |
| 消息中心 | 哪些消息需要先看？ | 不打开详情即可判断来源、严重度、时间和主操作 |
| 周报列表 | 哪份报告异常最严重？ | 一行比较周期、结论、异常、完整度、发布和投递状态 |
| 周报详情 | 本周发生了什么，依据是什么？ | 桌面首屏一分钟读完结论、指标和最严重异常 |
| 公告管理 | 谁会收到，何时失效？ | 发布前显示接收人数和影响摘要 |
| 投递管理 | 为什么失败，能否重发？ | 邮箱掩码、尝试次数、错误类别和下次重试同时可见 |

## 四、竞品与邻近产品评估

### 1. Tableau Pulse

值得借鉴：把当前值、对比变化、筛选范围和自动洞察放在同一阅读路径，并通过邮件或
Slack 摘要把用户带回详情；认证指标还能明确可信来源。

不能照搬：以单指标为中心的卡片模式不适合完整制造周报，多个指标卡平铺会削弱总体
结论和行动优先级。

来源：[Tableau Pulse 指标探索](https://help.tableau.com/current/online/en-us/pulse_explore_metrics.htm)、
[Tableau Pulse 指标定义](https://help.tableau.com/current/online/en-us/pulse_create_metrics.htm)

### 2. Microsoft Power BI

值得借鉴：移动视图不是桌面画布的等比缩放，而是只选择适合小屏的视觉并重新排序；
图表要求明确标题、替代文本、键盘顺序和可访问的数据表。

不能照搬：自由画布和大量切片器容易形成“看板墙”，ForgeSight 应保持报告叙事顺序，
筛选只改变范围，不打散结论。

来源：[Power BI 移动优化报告](https://learn.microsoft.com/en-us/power-bi/create-reports/power-bi-create-mobile-optimized-report-about)、
[Power BI 无障碍报告设计](https://learn.microsoft.com/en-us/power-bi/create-reports/desktop-accessibility-creating-reports)

### 3. Linear Inbox

值得借鉴：消息入口固定在侧栏，未读状态清楚；列表和单条详情之间切换快速，键盘操作
完整，用户可以在消息中心直接完成处理。

不能照搬：工程事件通常短且高频，周报和公告需要两行摘要、业务来源和更明确的严重度，
不能只显示事件标题。

来源：[Linear Inbox](https://linear.app/docs/inbox)、
[Linear Notifications](https://linear.app/docs/notifications)

### 4. Notion Inbox

值得借鉴：按来源内容聚合更新，支持未读/已读筛选和打开后直达相关上下文；移动端提供
适合触控的批量与滑动操作。

不能照搬：按页面或评论线程聚合不适合 ForgeSight。周报和公告是不可混淆的正式业务
对象，应保留类型、版本、优先级和发布状态。

来源：[Notion Inbox 与通知](https://www.notion.com/help/updates-and-notifications)

### 5. Stripe Reporting

值得借鉴：报告页服务于明确的业务任务，筛选和下载并列，数据可继续导出用于核对；
报告名称直接对应业务问题，而不是图表类型。

不能照搬：财务报表偏高密度和专业术语，ForgeSight 面向跨部门制造管理，需要先给中文
管理结论，再逐层显示指标定义和明细。

来源：[Stripe Reporting](https://docs.stripe.com/stripe-reports)、
[Stripe Payments Analytics](https://docs.stripe.com/payments/analytics)

### 6. Asana Inbox

值得借鉴：把 Inbox 定义为需要处理的更新而不是所有事件的日志，用户可以通过减少无关
订阅维持较低噪声。

不能照搬：ForgeSight 的公告接收范围由管理员和权限策略决定，业务用户不应自行取消
必须送达的正式公告。

来源：[Asana Inbox](https://help.asana.com/s/article/inbox)

## 五、用户已熟悉的行业模式

- 全局导航中有稳定的消息入口和未读数字，消息打开后变为已读；
- 列表负责浏览与比较，详情负责解释，不用相同卡片同时承担两种任务；
- 状态由文字和图标共同表达，颜色只做辅助；
- 指标必须同时给出单位、比较周期和变化方向；
- 图表回答一个明确问题，并提供文字结论或数据表，不把关键信息藏在悬停提示中；
- 下载动作明确区分 PDF 和 Excel，并显示文件是否就绪；
- 管理操作先显示影响范围，完成后提供可核验结果。

## 六、ForgeSight 的一个差异点

**结论与证据同屏可追溯。**

其他产品通常把自动洞察、看板和原始数据分开。ForgeSight 的周报应让每条关键结论都能
看到对应周期、指标口径、数据质量和证据入口，但证据位于阅读主线之后，不妨碍管理者
快速浏览。这一差异点应贯穿消息摘要、周报详情、PDF 和 Excel，而不是增加一个孤立的
“AI 说明”卡片。

## 七、非模板化视觉参考

### 1. 瑞士国际主义平面设计

转译内容：严格列网、非对称但可预测的版面、有限颜色和清楚的字号层级。用于报告身份、
指标带和章节节奏，避免同尺寸卡片网格。

### 2. 制造现场安灯与铁路运行图

转译内容：状态必须一眼可判、时间轴和责任对象明确、异常比装饰更醒目。用于严重度、
进度、投递状态和行动表格；不直接复制高饱和红绿灯墙。

### 3. 上市公司年度报告的编辑式跨页

转译内容：一句主结论引导图表，图注说明范围和来源，正文与数据表保持可阅读行长。
用于周报详情和 PDF 的视觉一致性；不复制宣传型大图和空泛品牌口号。

## 八、当前界面审计

### 可保留

- 已有侧栏、页面框架、基础按钮和状态标签形成了稳定产品壳层；
- 已有灰蓝中性色、克制阴影和圆角层级适合企业工具；
- 报告详情已有章节、结果表和证据面板，可以复用数据接入经验；
- 登录 API 已包含注册邮箱、验证码、换绑和 `emailStatus` 契约；
- 消息、公告、投递和报告文件后端 API 已稳定，可直接接真实状态。

### 必须修正

- 当前登录注册界面没有邮箱字段，也没有未验证用户的专用门禁页面；
- 导航没有消息入口和未读数，前端也没有消息、公告、投递 API 模块；
- 报告列表仍以“生成中/待确认/已发布”和人工复核文案为主，与自动发布流程冲突；
- 报告详情是章节目录、正文、证据三栏工具页，不是管理者优先的编辑式周报；
- 页面存在大量 10～13px 文本，达不到 U08 和最终 Web 检查表的阅读要求；
- 当前“导出/打印 PDF”仍指向旧 HTML 预览，没有呈现正式 PDF/Excel 文件任务状态；
- 图表为通用条形预览，没有把趋势、Pareto、异常与行动分别映射到最合适的视觉形式；
- 目前没有管理员公告和邮件投递管理页面。

## 九、设计约束与不做事项

- 不新增人工审核作为周报默认流程；Agent 校验通过后直接发布；
- 不用假数据、固定延迟或循环动画冒充 Agent、附件或投递进度；
- 不把完整邮箱、SQL 或敏感错误放进普通列表；
- 不使用 3D 图、无意义饼图、装饰性仪表盘、玻璃拟态或紫蓝渐变；
- 不把移动端处理成桌面三栏的缩小版；
- 不添加与 U03～U09 无关的新业务功能。

## 十、研究结论

U02 应以“经营简报 + 可追溯证据”为统一视觉框架：消息是入口，周报是叙事主体，图表
负责比较，表格负责核对，证据负责建立信任，管理员页面保持高密度操作体验。设计需要
同时支持桌面一分钟阅读和移动端三十秒判断，并优先复用现有品牌壳层而不是全站换肤。
