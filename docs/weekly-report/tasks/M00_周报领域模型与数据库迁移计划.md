# M00 周报领域模型与数据库迁移计划

> 大任务：`M周报领域模型`
> 目标：在现有报告模型上建立支持自动发布、不可变版本、文件、站内消息、公告和按用户投递的统一数据基础。
> 前置依赖：Q 的用户邮箱与身份契约
> 后续依赖：R、V、N、E、U、T

## 一、交付边界

本任务只负责领域模型、组织与数据权限、持久化事件、数据库迁移、状态约束和基础仓储，
不实现 Agent 生成、PDF 渲染、邮件发送或页面。

必须复用现有 `Report`、`ReportVersion`、`ReportSection`、`ReportSubscription`、`ReportDelivery`，禁止另建一套平行报告表。

## 二、现有代码接入点

- ORM：`backend/app/db/models.py`。
- 平台库初始化：`backend/app/db/platform.py`、`backend/scripts/init_db.py`。
- PostgreSQL schema：`database/postgresql/001_schema.sql`。
- 报告服务：`backend/app/reports/service.py`。
- 报告契约：`backend/app/reports/contracts.py`。
- 现有报告测试：`backend/tests/test_reports.py`。

## 三、执行步骤

### M01 固化领域状态与不变量

1. 定义报告主状态、版本状态、章节状态、文件状态、消息状态、公告状态和投递状态。
2. 明确报告“已发布”与邮件“已发送”是两个独立事实。
3. 定义不可变边界：已发布版本正文、数据快照和文件校验值不可修改。
4. 定义版本替代关系和当前版本指针更新规则。
5. 定义所有幂等键和唯一约束。

验收：状态转换表没有人工复核必经状态，非法转换可被服务端拒绝。

### M02 增量扩展报告与版本模型

1. `Report` 增加 `subscription_id`、`schedule_key`、
   `audience_scope_hash`、`publish_source` 等字段。
2. `ReportVersion` 增加 `supersedes_version_id`、`validation_json`、`workflow_version`、`model_snapshot_json`、`data_quality_json`。
3. 明确 `created_by=report-agent` 与实际调度任务的关系。
4. 为周期、模板版本和受众范围建立查询索引。
5. 旧报告字段保持可读，为历史 `reviewer_id` 提供兼容但不再作为新链路必填项。

验收：历史报告序列化不报错，新报告可表达自动发布来源和版本替代。

### M03 新增报告文件模型

1. 新增 `ReportFile`，绑定 `report_id` 和 `version_id`。
2. 字段包括 `format`、`status`、`storage_uri`、`mime_type`、`file_size`、`checksum`、`error_json`、生成时间。
3. 对 `version_id + format` 建唯一约束，阻止同版本成功文件被静默替换。
4. 存储 URI 只供后端使用，不直接作为公开下载链接。
5. 定义失败后重新生成时的 attempt 或任务记录关系。

验收：PDF 与 Excel 可独立成功、失败和重试。

### M04 新增统一消息与接收人模型

1. 新增 `Message`，字段覆盖类型、来源、标题、摘要、关联对象、优先级、置顶、有效期和状态。
2. 新增 `MessageRecipient`，记录用户、已读状态、已读时间和消息创建状态。
3. 对 `message_id + user_id` 建唯一约束。
4. 周报消息保存具体 `report_version_id`，避免当前版本变化后内容漂移。
5. 定义消息撤回与过期语义，周报消息不使用撤回修正。

验收：同一发布事件重试不会给同一用户创建重复消息。

### M05 新增管理员公告模型

1. 新增 `Announcement` 和必要的版本字段，保存正文、优先级、接收范围、置顶和有效期。
2. 状态支持草稿、已发布、已撤回、已过期。
3. 发布后正文不可直接改写；修订形成新版本或新公告记录。
4. 保存创建人、发布人、撤回人和对应时间。
5. 接收范围使用结构化 JSON，并保存规范化哈希用于审计。

验收：公告可以恢复发布当时的正文和接收范围。

### M06 扩展订阅与投递模型

1. `ReportSubscription` 默认渠道从 `feishu` 演进为 `email`，新订阅默认 `auto_publish`。
2. 保留历史飞书记录可读，不批量静默改写现有订阅行为。
3. `ReportDelivery` 增加 `recipient_user_id`、`recipient_address_snapshot`、`idempotency_key`、`next_retry_at`、`attempt_count`、`error_category`、`provider_message_id`。
4. 唯一约束覆盖版本、用户和渠道。
5. 区分一条业务投递与多次服务商发送尝试；必要时新增 `DeliveryAttempt`。

验收：同一用户同一报告版本只存在一个业务投递，可包含多次尝试。

### M07 建立组织成员与数据权限模型

1. 新增 `OrganizationUnit` 表达企业、区域、部门等树形组织节点。
2. 新增 `UserMembership` 表达用户所属组织、岗位和组织内业务角色。
3. 新增 `DataScopePolicy` 表达可访问的数据源、业务维度和值域，并与用户、组织或岗位关联。
4. 认证角色 `business/admin` 只控制平台操作权限，不替代业务组织角色。
5. 提供统一范围解析契约：输入用户和目标业务，输出显式接收资格与可执行数据范围。
6. 为组织层级、成员和策略生效时间建立必要索引和审计字段。

验收：显式用户、角色、部门、区域、岗位接收范围均能解析为用户集合和数据权限，
R、V、N、E 无需自行解释权限 JSON。

### M08 新增持久化 Outbox 事件模型

1. 新增 `DomainEventOutbox`，保存事件 ID、类型、聚合 ID、业务幂等键、payload、状态和创建时间。
2. 增加租约持有者、租约到期、尝试次数、下次重试时间、确认时间和错误摘要。
3. 对事件 ID 和业务幂等键建立唯一约束。
4. 业务状态变更与 Outbox 写入必须在同一数据库事务完成。
5. 状态支持 `pending`、`processing`、`retry_wait`、`completed`、`dead_letter`。
6. 提供租约领取、确认、失败退避和死信恢复仓储方法。

验收：模拟业务事务提交后进程崩溃，事件仍能被其他 Worker 领取并完成。

### M09 编写可重复数据库迁移

1. 提供 PostgreSQL 增量迁移，禁止删库重建。
2. 更新测试环境 SQLite 建表逻辑。
3. 在迁移前后验证表、索引、唯一约束和默认值。
4. 对历史 `after_review` 订阅保留原值并提供管理员迁移清单。
5. 添加向前迁移演练脚本或检查 SQL，不假设可无损向后降级。

验收：现有数据库副本迁移前后记录数一致，旧报告查询通过。

### M10 建立仓储方法与并发测试

1. 提供按幂等键获取或创建报告、消息和投递的事务方法。
2. 提供原子冻结版本、切换当前版本和建立替代关系的方法。
3. 对并发调度、并发发布、Outbox 领取、并发消息创建和并发投递创建写测试。
4. 验证唯一约束冲突能够转换为业务幂等成功或明确错误。
5. 禁止服务层先查后写而没有数据库约束兜底。

验收：并发执行不会生成重复版本、消息或投递。

## 四、建议状态枚举

```text
Report: scheduled, queued, checking_data, planning, running_sections,
        validating, composing, published,
        data_insufficient, partial, validation_failed, generation_failed

ReportFile: queued, generating, ready, failed
Message: published, withdrawn, expired
Delivery: queued, sending, sent, retry_wait, failed, suppressed
```

状态值集中定义，避免散落在前后端字符串中。

## 五、迁移验证清单

- 迁移前备份或快照平台库。
- 记录各相关表行数。
- 执行迁移两次，第二次不得破坏数据。
- 检查唯一索引和外键。
- 读取现有报告列表、详情和订阅。
- 创建新报告、版本、文件、消息和投递测试记录。
- 回收测试数据，不删除生产历史记录。

## 六、风险与回滚

- 风险：现有代码仍假设复核状态。缓解：模型先兼容旧状态，R/U 分阶段切换。
- 风险：大 JSON 字段索引不足。缓解：高频过滤字段独立列存，JSON 只保存快照。
- 风险：幂等约束设计过窄或过宽。缓解：以用户、版本、渠道和业务事件为边界写并发测试。
- 回滚：应用层可回退读取旧字段；新增表和列保留，不执行破坏性降级。

## 七、完成定义

- M01～M10 全部完成。
- PostgreSQL 与 SQLite 均支持新模型。
- 旧报告和飞书历史记录仍可读取。
- 数据库约束能阻止重复报告、消息和投递。
- 组织范围和数据权限可由统一服务解析。
- 业务提交与 Outbox 事件原子落库，消费者崩溃后可恢复。
- 已发布版本与文件具有不可变语义。
- 所有迁移与模型测试通过。
