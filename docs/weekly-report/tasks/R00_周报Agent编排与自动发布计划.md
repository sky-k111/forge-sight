# R00 周报 Agent 编排、调度与自动发布计划

> 大任务：`R周报Agent自动发布`
> 目标：复用现有分析 Run、Task 和 Artifact，按订阅周期自动生成结构化周报，通过校验门后直接发布。
> 前置依赖：M 领域模型；Q 提供有效用户身份
> 协作依赖：V 提供校验和文件契约，N/E 消费发布事件

## 一、交付边界

本任务负责调度、数据预检、报告章节编排、结果汇总、状态流转和自动发布事件。PDF/Excel 渲染属于 V，消息属于 N，邮件属于 E。

本任务不得恢复人工提交复核、批准或发布的必经流程。

## 二、现有代码接入点

- 报告服务：`backend/app/reports/service.py`。
- 报告模板：`backend/app/reports/templates.py`。
- 报告 API：`backend/app/api/reports.py`。
- Agent Worker：`backend/app/agent/worker.py`。
- Agent Run/Task/Artifact：`backend/app/agent/` 与 `backend/app/db/models.py`。
- 报告测试：`backend/tests/test_reports.py`、`backend/tests/test_agent_worker.py`。

## 三、执行步骤

### R01 定义周期和调度语义

1. 周期按订阅时区计算，默认自然周为周一至周日。
2. 定义首次运行、正常运行、漏跑补偿、禁用订阅和时区修改行为。
3. 为每次计划生成稳定 `schedule_key` 和幂等键。
4. 调度器只创建持久化任务，不在 Web 进程中直接完成长任务。
5. 明确多实例调度的租约与抢占规则。

验收：同一订阅同一周期并发触发只产生一个有效任务。

### R02 实现到期订阅扫描与任务创建

1. 扫描 `enabled` 且 `next_run_at <= now` 的订阅。
2. 使用数据库锁或唯一约束避免多 Worker 重复创建。
3. 创建报告业务身份和生成任务后，原子更新下次运行时间。
4. 失败时不跳过当前周期，保留可补偿状态。
5. 记录计划命中、跳过、补偿和禁用原因。

验收：重启进程后未完成任务能够恢复，漏跑周期能够补偿一次。

### R03 执行数据与指标预检

1. 检查数据源连接、模板启用状态、指标物理绑定和时间字段。
2. 检查本期与比较期是否完整。
3. 计算数据截止时间、覆盖率、缺失比例和延迟源。
4. 根据模板最低覆盖率判定正常生成或数据异常版周报。
5. 冻结本次使用的模板、指标和绑定版本。

验收：关键数据不可用时不会继续生成伪完整周报。

### R04 生成章节执行计划

1. 把模板章节映射为阶段五分析任务。
2. 为每个章节定义目标、指标、维度、比较策略、异常规则和输出 schema。
3. 对不可执行章节记录原因，不能静默丢失。
4. 限制总查询量、LLM 调用量、执行时长和输出 token。
5. 保存结构化计划，前端可以展示真实进度。

验收：计划可重复执行和审计，章节数及状态与报告详情一致。

### R05 执行章节并绑定证据

1. 复用现有只读 SQL 安全、预算、重试和 Artifact 流程。
2. 数值计算由 SQL/Python 完成，LLM 不直接计算关键指标。
3. 每个章节绑定分析 Run、Task、Artifact、指标版本和时间范围。
4. 章节失败独立记录；允许形成 `partial` 或数据异常版报告。
5. 不允许在未明确授权时跨数据源拼接。

验收：报告中每个数值结论可追溯，单章节失败不丢失已完成结果。

### R06 生成摘要、异常与行动建议

1. 基于已经验证的结构化章节结果生成管理摘要。
2. 选择 3～5 条有决策价值的发现，过滤小幅噪声和重复结论。
3. 异常按严重程度、影响范围和证据强度排序。
4. 原因字段严格使用已证实、可能相关、待调查三类。
5. 行动建议包含优先级、建议负责人、期限和预期效果，但不自动创建工单。

验收：摘要不包含无证据数字，原因措辞与证据状态一致。

### R07 接入自动发布校验门

1. 调用 V 定义的确定性校验器。
2. 硬校验失败进入 `validation_failed`，不得发布正常周报。
3. 软校验失败降低可信度并写入醒目限制说明。
4. 关键数据不足时构建数据异常版周报。
5. 保存全部校验结果和工作流版本。

验收：不存在“LLM 自己认为正确就发布”的路径。

### R08 冻结版本并直接发布

1. 在事务中冻结结构化版本、设置发布时间并切换 `current_version_id`。
2. 记录 `publish_source=agent`，不填写伪造的人工审核人。
3. 在同一事务中写入稳定的 Outbox 发布事件，供 V、N、E 至少一次消费。
4. 重试时依据幂等键返回已有成功结果。
5. 重新生成时创建新版本并建立替代关系。

验收：校验通过后自动进入 `published`，不会停留在 `awaiting_review`。

### R09 完成恢复、重试与测试

1. 测试 Worker 崩溃、租约过期、数据库短暂失败和 LLM 超时。
2. 测试重复调度、重复事件消费、并发发布，以及提交发布事务后进程立即崩溃。
3. 测试关键数据缺失、局部章节失败和比较期不完整。
4. 测试已发布版本不可被原任务重新写入。
5. 验证状态事件序列可供前端真实展示。

验收：所有失败都有可恢复或明确终止语义，不生成重复用户触达。

## 四、发布事件契约建议

```json
{
  "eventType": "report.version.published",
  "eventId": "evt_xxx",
  "reportId": "report_xxx",
  "versionId": "rv_xxx",
  "subscriptionId": "sub_xxx",
  "period": {"start": "...", "end": "...", "timezone": "Asia/Shanghai"},
  "audienceScopeHash": "sha256...",
  "publishedAt": "..."
}
```

事件消费者必须按 `eventId` 或业务幂等键去重。

## 五、风险与回滚

- 风险：自动发布放大错误结论。缓解：硬校验门、证据绑定、数据异常版和逐模板灰度。
- 风险：调度器重复执行。缓解：数据库唯一约束、租约和幂等消费。
- 风险：大范围用户产生高负载。缓解：按报告生成一次，按权限分群或生成专属版本，触达异步化。
- 回滚：可禁用具体订阅或全局调度开关；已发布版本不删除，必要时发布替代版本。

## 六、完成定义

- R01～R09 全部完成。
- 周报可定时、可恢复、可追溯地生成。
- Agent 校验通过后直接发布，无人工复核阻塞。
- 数据不足时不伪造结论。
- 重复调度和重试不产生重复报告版本。
- 发布事件可被文件、消息和邮件链路幂等消费。
- 发布事件与版本状态原子提交，进程崩溃不会永久丢失下游任务。
