# ForgeSight 周报、消息中心与邮件推送产品需求文档

> 文档状态：待团队评审
> 需求版本：V1.0
> 产品范围：Web 端、FastAPI 后端、平台数据库、Agent Worker、文件导出与邮件服务
> 目标用户：管理员、管理层用户、普通业务用户
> 更新日期：2026-08-13

## 1. 背景与问题

ForgeSight 已具备数据源治理、企业知识、Agent 分析和初步报告能力，但当前报告流程仍以用户主动创建、人工复核和飞书推送为核心。
新的产品目标是让系统主动完成固定周期的经营分析：周报 Agent 按计划生成周报，通过确定性校验后直接发布到站内消息中心，
同时把摘要、详情链接和 PDF 附件发送到用户绑定的邮箱。

本需求解决四个问题：

1. 用户不需要每天主动打开多个页面寻找经营变化。
2. 管理层能在一分钟内看懂本周结论、异常、风险和建议。
3. 周报结论可以追溯到指标、数据范围和证据，避免 Agent 无依据发挥。
4. 站内消息和邮箱形成稳定触达闭环，渠道失败不影响报告本身发布。

## 2. 产品目标

### 2.1 目标

- Agent 按自然周自动生成并直接发布结构化周报。
- 周报回答“发生了什么、为什么重要、可能原因、下一步做什么、数据是否可信”。
- 管理员公告和 Agent 周报统一进入站内消息中心。
- 用户登录体系增加强制邮箱绑定与所有权验证。
- 任意有效邮箱均可接收周报和公告。
- 周报邮件正常情况下包含 3～5 条摘要、安全链接和对应版本 PDF；
  超过已配置附件上限时允许显式降级为摘要和链接。
- 站内提供 PDF 正式报告和 Excel 数据明细下载。
- 发布、附件生成和邮件投递具有独立状态、重试与审计能力。

### 2.2 成功指标

- 定时任务按期创建率不低于 99%。
- 已满足数据条件的周报自动发布成功率不低于 98%。
- 同一用户、周期、版本不产生重复站内消息或重复邮件。
- 邮件首次投递成功率可观测，失败任务自动重试后可被管理员定位。
- 周报中所有数值结论均能关联到数据源、统计范围、指标版本或分析 Artifact。
- 无权限用户不能通过页面、链接、PDF 或 Excel 获得越权数据。
- 站内周报与 PDF 采用统一且精美的编辑式视觉系统，真实图表、业务图片和表格不是可选装饰，而是报告正文的一部分。

## 3. 非目标

本期不包含：

- 人工审批、会签或周报发布前复核流程。
- Word 式自由排版编辑器。
- 用户在消息中心聊天、回复或要求公告确认回执。
- 把行动建议自动转换成完整工单系统。
- 多语言周报。
- 短信、微信、钉钉等更多外部渠道。
- 让 Agent 在没有数据证据时推断确定性因果关系。

飞书适配代码可以保留兼容，但不属于本期主链路和验收阻断项。

## 4. 已确认产品决策

| 事项 | 已确认决策 |
| --- | --- |
| 发布方式 | Agent 校验通过后直接发布，无人工审核 |
| 使用角色 | 管理员、管理层用户、普通业务用户均可使用 |
| 消息类型 | Agent 周报、管理员公告 |
| 公告回执 | 不要求用户确认，打开后自动标记已读 |
| 登录方式 | 保留账号密码登录，强制绑定并验证邮箱 |
| 邮箱范围 | 任意有效邮箱，不限制 QQ 邮箱 |
| 周报邮件 | 摘要 + 安全链接 + PDF 附件 |
| 周报下载 | PDF + Excel；Excel 默认不随邮件发送 |
| 权威版本 | 站内已发布的不可变报告版本 |
| 渠道失败 | 不回滚站内发布，进入独立重试流程 |
| 通知偏好 | 首期周报与重要公告不可关闭，后续再增加偏好设置 |

## 5. 用户与权限

### 5.1 管理员

- 配置周报模板、周期、时区、发送时间、接收范围和数据最低完整度。
- 发布、置顶、设置有效期和撤回管理员公告。
- 查看生成任务、附件任务和邮件任务状态。
- 查看失败原因并触发受控重试。
- 查看审计记录，但仍受数据权限限制。

### 5.2 管理层用户

- 接收权限范围内的企业、区域或部门经营周报。
- 优先查看管理摘要、指标变化、风险排序和行动建议。
- 查看证据、下钻详情并下载 PDF/Excel。

### 5.3 普通业务用户

- 接收与本人部门、岗位或业务范围相关的周报和公告。
- 查看相关指标、异常和建议。
- 不能读取超出本人数据权限的正文、附件和链接。

### 5.4 权限原则

权限必须在四个环节独立执行：

1. Agent 生成时裁剪数据范围。
2. API 读取时校验报告接收关系和数据范围。
3. PDF/Excel 生成及下载时校验版本和权限。
4. 邮件创建时根据接收人权限选择专属版本或安全摘要。

不能仅依靠前端隐藏按钮，也不能把一个包含全量数据的 PDF 发送给只有局部权限的用户。

组织与数据权限必须落到平台库的正式模型：认证角色继续表示 `business/admin`，
组织角色、部门、区域、岗位和数据范围通过独立的组织成员关系与权限策略表达。
接收范围解析服务负责把规则展开为显式用户集合和可执行数据范围，R、V、N、E 统一复用，
禁止各模块自行解释权限 JSON。

## 6. 核心用户流程

### 6.1 新用户注册

1. 用户填写用户名、密码、展示名和邮箱。
2. 系统创建待验证账号并发送六位邮箱验证码。
3. 用户提交验证码。
4. 验证成功后账号激活并进入工作台。
5. 验证前只允许访问登录、注册、重发验证码和验证页面。

### 6.2 存量用户首次登录

1. 用户使用原账号密码登录。
2. 系统发现账号未绑定已验证邮箱。
3. 返回受限会话或明确的 `email_binding_required` 状态。
4. 前端强制进入邮箱绑定页。
5. 用户完成验证码验证后进入工作台。

### 6.3 周报自动发布

1. 调度器根据订阅的时区和周周期创建幂等任务。
2. Agent 检查数据刷新时间、指标覆盖率与权限范围。
3. Agent 计算指标、识别异常并生成结构化章节。
4. 系统执行确定性数值、权限、内容和数据质量校验。
5. 校验通过后，在同一事务中冻结报告版本、标记为已发布并写入持久化 Outbox 事件。
6. Outbox 消费者创建目标用户的站内周报消息。
7. 独立文件任务生成该版本 PDF 和 Excel。
8. PDF 可用后写入文件就绪事件，邮件消费者发送摘要、链接和 PDF。
9. 每个消费者独立确认、重试和记录结果；渠道失败不改变报告已发布状态。

### 6.4 管理员发布公告

1. 管理员填写标题、正文、重要程度、接收范围、置顶状态和有效期。
2. 系统预估接收人数并校验权限范围。
3. 管理员确认发布。
4. 系统创建不可变公告版本及每位用户的站内消息。
5. 根据公告等级创建邮件任务。
6. 用户打开消息后自动标记已读，不需要回执。

## 7. 周报详细需求

### 7.1 周报定位

周报不是指标堆砌，也不是把一周全部数据复制成表格。它是一份面向决策的结构化分析，应优先回答：

1. 本周整体表现如何？
2. 哪些变化最值得关注？
3. 异常影响了哪些范围？
4. 原因已证实还是仍需核查？
5. 下一步应由谁在什么时间内做什么？
6. 数据是否完整，结论可信度如何？

### 7.2 报告身份信息

每个已发布版本必须固化以下字段：

| 字段 | 规则 |
| --- | --- |
| 标题 | 包含组织或主题，例如“华东工厂经营周报” |
| 报告周期 | 明确起止时间和时区 |
| 自然周标识 | 例如 `2026-W33`，用于幂等和文件名 |
| 版本号 | 从 V1 递增，不覆盖旧版本 |
| 数据源 | 一份报告默认绑定一个数据源 |
| 数据截止时间 | 使用数据的最晚更新时间 |
| 生成时间 | Agent 完成结构化内容的时间 |
| 发布时间 | 版本正式对用户可见的时间 |
| 生成主体 | Agent 名称、工作流版本和模型快照 |
| 接收范围 | 用户、角色、部门、区域或组织范围 |
| 数据完整度 | 完整、部分缺失、严重缺失 |
| 可信度 | 高、中、低，并附原因 |

### 7.3 管理摘要

管理摘要位于页面首屏和 PDF 第一页，目标是让用户在一分钟内理解本周状态。必须包含：

- 一句话总体结论。
- 3～5 条最重要发现，每条包含指标、变化、影响范围和业务意义。
- 本周最严重异常及严重程度。
- 最大风险及潜在影响。
- 1～3 条优先行动建议。
- 数据质量或统计口径提示。

摘要不得出现原始 SQL、物理字段名、内部数据库 ID 或无法解释的技术状态码。

### 7.4 核心指标概览

每个指标至少包含：

- 本周值和单位。
- 环比上周绝对变化及变化率。
- 有完整历史数据时提供同比。
- 存在目标时提供目标值、偏差和完成率。
- 趋势方向：上升、下降、持平。
- 业务状态：正常、关注、预警、严重。
- 指标口径版本、数据来源和更新时间。
- 有利方向，避免把“上升”一律理解为正面。

指标展示使用“结论 + 数值 + 比较 + 影响”的完整句式。例如：

> 本周订单量 12,460 单，环比下降 8.4%，下降主要集中在华东区域，并低于周目标 6.1%。

### 7.5 变化与趋势

Agent 应识别并排序：

- 超过业务阈值的周环比或同比变化。
- 连续多周同方向变化。
- 周内突变或异常时间点。
- 区域、部门、产品、产线、设备或客户群之间的结构差异。
- 与目标、预算或历史正常区间的偏离。

系统过滤重复、小幅且无行动价值的噪声。趋势图必须与正文使用同一指标版本、筛选范围和时间口径。

### 7.6 异常与风险

每项异常使用统一结构：

| 字段 | 要求 |
| --- | --- |
| 异常名称 | 使用业务语言描述问题 |
| 严重程度 | 严重、预警、关注、提示 |
| 发现时间 | 首次出现和最近出现时间 |
| 影响指标 | 关联一个或多个指标 |
| 影响范围 | 部门、区域、产品、客户或时间段 |
| 变化证据 | 当前值、基准值、偏差值和趋势 |
| 原因状态 | 已证实、可能相关、待调查 |
| 原因说明 | 区分事实、推断和未知项 |
| 潜在影响 | 不处理可能造成的后果 |
| 建议动作 | 具体核查或处置建议 |
| 详情入口 | 指向站内证据或分析页面 |

Agent 不得把相关性写成确定因果。证据不足时必须使用“可能相关”或“建议核实”，并降低可信度。

### 7.7 重点进展

周报不仅报告问题，也应覆盖：

- 目标完成或超额完成项。
- 重点项目、订单、客户或生产任务进展。
- 表现突出的区域、部门、产品或产线。
- 已关闭的上周风险。
- 值得复用的成功经验。

### 7.8 行动建议

每条建议包含：

| 字段 | 规则 |
| --- | --- |
| 建议事项 | 明确做什么，不使用空泛表述 |
| 依据 | 关联指标、异常或风险 |
| 优先级 | 高、中、低 |
| 建议负责人 | 用户、岗位或部门；无法判断则为待分配 |
| 建议期限 | 明确日期或相对时限 |
| 预期效果 | 希望改善的指标或降低的风险 |
| 跟踪状态 | 首期展示待处理；后续可接任务系统 |

本期建议不自动创建真实工单，避免 Agent 未经业务确认直接分派组织任务。

### 7.9 数据质量与可信度

周报必须公开分析基础：

- 使用的数据源和数据截止时间。
- 数据覆盖率、缺失比例与延迟源。
- 异常值、重复值或口径冲突。
- 与上一版本相比发生变化的指标口径。
- 各章节可信度和整份报告可信度。
- 未完成分析项及原因。

关键数据严重缺失时，系统不得生成看似完整的结论。应发布“数据异常版周报”，只展示已确认信息、缺失范围、影响和管理员排查入口。

### 7.10 附录与证据

附录承载：

- 指标定义和版本。
- 数据源、统计范围和更新时间。
- 图表规格与详细指标表。
- 异常明细。
- 关联分析 Run、Artifact 和结果集。
- SQL 或技术证据的受权限保护入口。
- Agent 工作流版本、限制和失败章节。

普通用户正文不直接展示原始 SQL；具有相应权限的用户可以在证据面板查看。

### 7.11 精美布局、图片、图表与表格

站内周报和 PDF 必须采用同一套 ForgeSight 报告视觉语言，目标是“像经过专业编辑设计的经营简报”，而不是连续堆叠的默认卡片或纯文本页面。

#### 阅读层级

用户打开报告后，视线顺序应稳定为：

1. 报告标题、周期、版本和数据可信度。
2. 一句话总体结论和 3～5 条管理摘要。
3. 核心指标与最严重异常。
4. 趋势、结构和业务图片。
5. 异常表、行动计划表和数据质量说明。
6. 证据与附录。

管理摘要与关键风险必须在桌面首屏和 PDF 第一页出现。章节之间使用明显的标题、留白和版式节奏，不允许把所有信息包装成尺寸相同的卡片网格。

#### 图片要求

每份正常周报至少包含一项有业务意义的图片内容，可按优先顺序选择：

1. 企业已授权的工厂、车间、产线、设备或产品图片。
2. 与本周异常或重点进展直接相关的业务图片。
3. 无合适业务照片时，使用由真实数据生成的主题洞察图、流程图或带注释的分析图作为视觉主图。

图片必须：

- 与所在章节结论直接相关，禁止使用无关图库图或纯装饰性“AI 科技图”。
- 标注标题、说明、来源和时间；外部或生成素材记录来源与使用权限。
- 提供替代文本，保证无法查看图片时仍能理解信息。
- 不包含未经授权的人员肖像、敏感设备信息或越权业务数据。
- 在 Web 和 PDF 中保持清晰，不拉伸、不裁掉关键内容。

数据不足版周报可以不使用业务照片，但必须提供清晰的数据状态图示。

#### 图表要求

图表根据分析问题选择，不追求数量：

| 分析问题 | 推荐图表 | 禁止用法 |
| --- | --- | --- |
| 随时间变化 | 折线图、面积趋势图 | 用饼图表示时间趋势 |
| 目标与实际 | 子弹图、组合图、进度条 | 只用孤立大数字 |
| 排名与贡献 | 横向条形图、Pareto 图 | 3D 柱形图 |
| 结构占比 | 条形占比图；类别很少时使用环形图 | 类别过多仍用饼图 |
| 两变量关系 | 散点图 | 暗示未经证实的因果关系 |
| 多维异常 | 热力图、矩阵图 | 仅用颜色表达且无标签 |

图表必须使用真实数据，显示单位、时间范围、图例和必要的数据标签；正文中引用的数值必须与图表一致。颜色不能作为唯一的信息载体，异常状态同时使用文字、符号或纹理。图表应支持查看说明和数据来源。

#### 表格要求

表格用于需要精确比较或查阅的内容，至少包括异常明细表和行动建议表。要求：

- 数字右对齐，文本左对齐，状态和短日期可居中。
- 单位放在表头或字段说明中，不在每个单元格重复。
- 按业务优先级排序，严重异常默认排在前面。
- Web 端支持固定表头、合理列宽、换行和小屏横向滚动。
- PDF 跨页时重复表头，禁止固定行高导致文字被截断。
- 长表默认只显示 Top N，完整明细进入 Excel 或展开区。
- 空值、未知值和零必须有不同语义，不能都显示为 `-`。

#### 视觉一致性与可访问性

- 实施前先完成 Web 报告页面与 A4 PDF 的设计 brief，并获得确认后再编码。
- 复用 ForgeSight 品牌与现有设计 token；为报告定义明确的字体、色彩、间距、圆角、表格和图表 token。
- 正文文本与背景对比度达到 WCAG AA；状态不能只依靠颜色。
- 正文保持舒适行长和行距，避免密集文字墙。
- Web 端在 375px 与 1440px 下均可阅读；PDF 打印不溢出、不重叠、不出现孤立标题。
- 加载使用内容骨架；空状态说明缺少什么以及原因；错误状态提供明确的恢复动作。
- 动效仅用于说明展开、切换和状态变化，并尊重 `prefers-reduced-motion`。

## 8. Agent 编排与自动发布

### 8.1 状态机

```text
scheduled
  -> queued
  -> checking_data
  -> planning
  -> running_sections
  -> validating
  -> composing
  -> published
```

允许的异常状态：`data_insufficient`、`partial`、`validation_failed`、`generation_failed`。
版本发布后，附件进入独立 `ReportFile` 状态机，消息和邮件进入各自投递状态机，均不混入报告主状态。

### 8.2 自动发布校验门

自动发布前必须全部通过以下硬校验：

1. 报告周期、时区和数据源明确。
2. 用户或组织接收范围可计算且权限规则有效。
3. 正文中引用的数值与结构化指标结果一致。
4. 环比和同比仅在两个完整周期均可用时生成。
5. 每个重要结论具备指标或 Artifact 证据。
6. 因果表述符合证据状态。
7. 敏感字段未进入无权限版本。
8. 报告身份、管理摘要、异常、建议和数据质量章节存在。
9. 幂等键未对应已成功发布的同版本任务。

软校验失败可以发布，但必须降级可信度并显示提示；硬校验失败不得发布正常周报。

### 8.3 幂等规则

建议幂等键：

`subscription_id + period_start + period_end + audience_scope_hash + template_version`

同一幂等键最多存在一个成功发布的主报告。任务重试复用原报告或创建明确的新尝试记录，不能给用户重复创建消息。

### 8.4 版本规则

- 已发布 `ReportVersion` 不可修改。
- 内容修复或重新生成产生 V2、V3 等新版本。
- 新版本建立 `supersedes_version_id` 关系。
- 消息和邮件记录绑定具体 `version_id`。
- 旧版本保留审计可见性，但默认入口跳转到当前版本。
- 邮件附件校验值必须与 `ReportFile` 记录一致。

## 9. 站内消息中心

### 9.1 信息架构

消息中心是统一的业务通知入口，不是聊天窗口。页面包含：

- 全部。
- Agent 周报。
- 管理员公告。

支持未读数、已读/未读筛选、时间排序、重要程度、置顶和有效期。

### 9.2 消息卡片

每条消息展示：

- 消息类型和来源。
- 标题。
- 发布时间。
- 两行摘要。
- 重要程度。
- 已读/未读状态。
- 主操作。

周报主操作为“查看周报”，次操作为“下载 PDF”；公告主操作为“查看公告”。

### 9.3 已读语义

- 打开消息详情后标记为已读。
- 已读状态按接收用户单独记录。
- 公告不要求确认回执。
- 撤回公告后消息标记为已撤回，保留管理员审计记录。
- 周报不使用撤回修正，采用新版本替代。

## 10. 管理员公告

公告字段包括：标题、正文、重要程度、发布人、接收范围、是否置顶、生效时间、过期时间和版本。

发布规则：

- 只有管理员可以创建、发布、撤回公告。
- 发布前显示预计接收人数。
- 公告发布形成不可变版本。
- 重要公告同步发送邮件；普通公告首期也按已确认需求默认发送。
- 邮件失败不影响站内公告。

## 11. 邮箱绑定与验证

### 11.1 邮箱规则

- 支持所有符合标准格式且能够收信的邮箱。
- 邮箱保存前统一去除首尾空格并规范化域名大小写。
- 默认一个已验证邮箱只绑定一个账号，避免身份和退订歧义。
- 更换邮箱必须验证新邮箱，成功前旧邮箱继续有效。
- 用户不需要向 ForgeSight 提供邮箱密码或个人邮箱授权码。

### 11.2 验证码规则

- 六位数字验证码。
- 有效期建议 10 分钟。
- 60 秒内不允许重复发送。
- 单个邮箱、账号和 IP 均设置小时级频率限制。
- 验证码只存哈希，不存明文。
- 连续输错达到上限后使本次挑战失效。
- 成功使用后立即失效。
- 错误提示避免泄露邮箱是否已注册。

### 11.3 登录门禁

登录接口仍校验账号密码，但对未验证邮箱的用户返回受限状态。受限 token 只能调用邮箱绑定、重发、验证、退出和当前状态接口，不能访问业务或管理 API。

## 12. 邮件推送

### 12.1 周报邮件

主题建议：

`【ForgeSight 周报】华东工厂经营周报｜2026年第33周`

正文固定包含：

1. 周报标题、周期和版本。
2. 3～5 条核心发现。
3. 最重要异常和严重程度。
4. 数据完整度或风险提示。
5. 登录后查看完整周报的安全链接。
6. 与站内版本一致的 PDF 附件。

Excel 默认不作为附件，只在站内通过鉴权下载。

### 12.2 安全链接

- 链接指向站内路由，不把一次性文件存储地址暴露在邮件中。
- 未登录用户先进入登录页，登录后回跳原周报。
- API 再次检查用户是否为消息接收人及是否具备对应数据权限。
- 链接不得在 URL 中携带敏感字段、邮箱或长期访问令牌。

### 12.3 投递状态

建议状态：`queued`、`sending`、`sent`、`retry_wait`、`failed`、`suppressed`。

每次尝试记录服务商消息 ID、开始/结束时间、错误类别和错误摘要。默认最多自动重试 3 次，采用指数退避并加入随机抖动。永久错误（邮箱格式无效、明确拒收）不做无意义重试。

### 12.4 降级策略

- PDF 暂时失败：报告继续保持已发布，等待附件任务成功后再发周报邮件。
- PDF 超过服务商附件上限：发送摘要与安全链接，记录 `attachment_omitted` 原因。
- 邮件服务不可用：任务进入重试，不回滚站内消息。
- 单个用户邮箱失效：只影响该接收人，不影响同批其他用户。

## 13. 下载与文件

### 13.1 PDF

- PDF 是正式阅读版本，与已发布结构化内容一一对应。
- 包含标题、周期、版本、数据截止时间、生成时间和页码。
- 文件名：`企业经营周报_2026-W33_V1.pdf`。
- 生成后记录存储地址、大小、MIME 类型、SHA-256 和生成状态。
- 同版本文件生成成功后不可被静默替换。

### 13.2 Excel

至少包含以下工作表：

- 指标概览。
- 异常明细。
- 行动建议。
- 数据来源与口径。

Excel 导出记录报告版本、导出时间和数据范围，下载接口实时校验权限。

## 14. 数据模型增量建议

在现有 `Report`、`ReportVersion`、`ReportSection`、`ReportSubscription`
和 `ReportDelivery` 基础上增量演进：

| 对象 | 主要增量 |
| --- | --- |
| `PlatformUser` | `email`、`email_verified_at`、绑定状态 |
| `OrganizationUnit` | 企业、区域、部门等组织节点及层级关系 |
| `UserMembership` | 用户与组织、岗位、业务身份的成员关系 |
| `DataScopePolicy` | 用户/角色/组织可访问的数据源、维度和值域规则 |
| `EmailVerificationChallenge` | 用途、验证码哈希、过期时间、尝试次数、使用时间 |
| `Report` | 调度/幂等键、受众范围哈希、自动发布来源 |
| `ReportVersion` | 替代版本、校验结果、Agent/工作流版本、数据完整度 |
| `ReportFile` | PDF/Excel 文件元数据、校验值和生成状态 |
| `Message` | 类型、标题、摘要、来源、关联对象、优先级、有效期 |
| `MessageRecipient` | 接收用户、已读状态和已读时间 |
| `Announcement` | 公告正文、版本、接收范围和发布状态 |
| `ReportDelivery` | 接收人、邮箱快照、幂等键、下一次重试时间和错误分类 |
| `DomainEventOutbox` | 事务内保存发布/文件事件、租约、尝试次数和确认状态 |

平台库 schema 变更必须使用可重复迁移，不删除或重建现有数据库。

### 14.1 持久化事件可靠性

报告发布、文件就绪和公告发布必须使用事务 Outbox：业务状态和事件在同一数据库事务提交。
后台消费者以租约领取事件，成功后确认；失败后记录错误并延迟重试，超过上限进入可恢复的死信状态。
消费者仍需使用业务唯一键实现幂等，因为 Outbox 保证事件不丢失，但允许至少一次投递。

## 16. 可观测性与审计

需要记录：

- 调度计划命中、跳过和补偿执行。
- Agent 各阶段耗时、失败步骤和重试次数。
- 报告校验项及失败原因。
- PDF/Excel 生成耗时、大小和校验值。
- 每位用户的消息创建结果。
- 邮件发送、重试、服务商响应和最终状态。
- 邮箱绑定、变更和验证安全事件。
- 管理员公告创建、发布、撤回与接收范围。
- 报告和文件访问审计。

日志不得记录验证码、邮箱服务凭据、完整访问令牌或未脱敏敏感数据。

## 17. 验收标准

### 17.1 邮箱与登录

- 新用户未验证邮箱前不能访问工作台。
- 存量用户首次登录被引导绑定邮箱。
- 任意可收信邮箱均可完成验证。
- 验证码具有过期、频控、错误次数和一次性使用限制。
- 系统不要求用户提交邮箱密码或授权码。

### 17.2 周报

- 定时任务能为目标周期创建唯一周报任务。
- 周报包含管理摘要、核心指标、趋势、异常、重点进展、行动建议、数据质量和证据。
- 每份正常周报具有专业编辑式布局，包含至少一项有业务意义的图片内容、必要的数据图表、异常明细表和行动建议表。
- Web 与 A4 PDF 的标题层级、颜色语义和数据内容一致，所有页面无文字截断、图表模糊或表格溢出。
- 重要结论均可追溯到结构化证据。
- 校验通过后由 Agent 直接发布，不出现人工审核阻塞状态。
- 关键数据不足时不伪造结论，并生成明确的数据异常说明。
- 重新生成形成新版本，历史版本不被覆盖。

### 17.3 消息与公告

- 周报发布后目标用户获得一条站内消息。
- 管理员公告按接收范围创建消息。
- 用户可以分类、筛选并标记已读。
- 公告不要求确认回执。
- 越权用户无法读取消息关联内容。

### 17.4 下载与邮件

- 用户可下载当前权限范围内的 PDF 和 Excel。
- 正常大小的周报邮件包含摘要、安全链接和正确版本 PDF；超过已配置附件上限时，
  允许显式降级为摘要和链接，并记录 `attachment_omitted`。
- Excel 不默认随邮件发送。
- 邮件失败不影响站内报告和消息。
- 失败投递可自动重试、管理员可查看并手动重发。
- 同一用户不会收到同一版本的重复邮件。

## 18. 兼容与迁移策略

1. 保留现有报告表并做增量迁移，不丢失已有报告。
2. 现有 `after_review` 订阅显式迁移为停用或由管理员确认，不能悄悄改变历史行为。
3. 新建周报订阅默认 `auto_publish` 和 `email` 渠道。
4. 飞书配置和历史投递继续可读，但不作为首期邮件功能的依赖。
5. 前端分阶段切换：先支持新接口兼容态，再移除人工复核主操作。
6. 所有新表和唯一约束先在 SQLite 测试与 PostgreSQL 迁移脚本中验证。

## 19. 默认假设

以下事项尚未要求额外产品选择，首期按默认方案执行：

- 自然周为周一 00:00 至周日 23:59:59，按订阅时区计算。
- 典型发送时间为下周一 09:00，可由管理员配置。
- 邮箱验证码有效期 10 分钟，重发间隔 60 秒。
- 邮件自动重试最多 3 次。
- 周报与重要公告邮件不可关闭。
- 一个已验证邮箱默认只绑定一个账号。
- PDF 附件大小超过服务商限制时允许降级为摘要和链接。

这些默认值应配置化，后续产品决策可调整，而不改变核心领域模型。
