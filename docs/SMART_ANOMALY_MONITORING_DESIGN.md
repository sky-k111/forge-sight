# ForgeSight 智能异常监控与警报设计方案

> 文档状态：设计草案
> 适用项目：ForgeSight 制造业数据分析与决策支持平台
> 目标读者：产品、后端、前端、数据治理、测试与部署人员
> 最后更新：2026-08-26

## 1. 文档目的

本文给出 ForgeSight“智能异常监控与警报”能力的完整设计，明确：

- 产品定位、用户角色和业务范围；
- 当前项目中可以直接复用、需要扩展和不应复用的能力；
- 新数据源接入后的语义映射、指标绑定和监控规则形成流程；
- 监控任务、规则评估、警报事件、通知投递和自动恢复的端到端实现；
- 前后端接口、权限、安全、审计、部署、可观测性和测试要求；
- 分阶段实施顺序和验收标准。

本文是后续开发的总体设计基线。实际编码应再拆分为数据库迁移、后端契约、前端交互、消息渠道和交付测试等独立任务。本文所称“验收”仅指软件交付与测试验收，不表示监控模块参与异常的业务确认、处置验收或工单关闭。

## 2. 产品定位

### 2.1 推荐名称

产品能力统一命名为：

> **智能异常监控与警报**

不建议命名为“设备故障预测”，原因是当前主要数据来自 MES、QMS、设备停机和库存等关系型业务表，缺少秒级设备遥测、报警流、振动、温度、电流等传感器数据。当前系统能够可靠实现的是生产经营异常监控、已发生停机告警和数据质量监控，而不是真正的实时预测性维护。

### 2.2 产品价值

ForgeSight 从“用户主动提问后分析”扩展为“系统主动发现变化并及时告警”：

```text
受控取数 → 数据质量检查 → 规则评估 → 警报触发/持续/升级 → 通知 → 自动恢复
```

系统不是 MES、QMS、EAM 或 WMS 的替代品，而是建立在现有企业数据底座之上的受治理决策支持层。

### 2.3 核心用户

| 用户 | 主要需求 | 系统价值 |
|---|---|---|
| 生产主管、车间主任 | 及时获知计划偏差、产量下降和产线异常 | 按影响查看警报，定位工单、产线和时间窗口 |
| 质量工程师、质量主管 | 及时获知不良率上升、异常批次和缺陷集中 | 查看样本量、基线、Pareto、工序和产品证据 |
| 设备工程师、维修计划员 | 及时获知非计划停机、长停和重复停机 | 查看重点设备、产线、工单和历史观测 |
| 计划与库存人员 | 及时获知工单进度、缺料和安全库存风险 | 查看缺口、持续时间和影响对象 |
| 厂长、运营负责人 | 知道当前最需要关注的风险 | 查看严重警报、持续时长和恢复状态 |
| 班组长、现场人员 | 接收与本人数据范围相关的警报 | 通过 Web、飞书或钉钉查看事实与证据 |
| 数据与治理管理员 | 保证指标、字段、规则和权限正确 | 审核语义绑定、规则版本和数据质量 |

## 3. 业务范围

### 3.1 第一版纳入范围

完整规则库可覆盖以下数据域，但第一版 MVP 只启用“数据断流、工序良率下降、非计划停机”三类规则，以验证一条稳定的监控与警报链路。

#### 数据更新与断流

- 数据源不可连接；
- 业务表最大时间未推进；
- 数据延迟超过预期更新周期；
- 当前周期数据覆盖不足；
- 必填字段缺失、重复记录或枚举漂移。

#### 生产异常

- 产量下降；
- 产线间明显偏差；
- 计划产量与实际进度不匹配；
- 工单临近结束但完成度不足；
- 返工量或报废量异常上升。

#### 质量异常

- 工序良率下降；
- 抽检不良率上升；
- 缺陷类型集中；
- 产品、工序或产线成为异常贡献项；
- 样本量不足导致结论不可靠。

#### 设备与停机异常

- 单次非计划停机过长；
- 设备累计停机时长异常；
- 短停频率异常；
- 同类停机复发；
- 停机与产量下降在时间上重合。

#### 库存异常

- 可用库存低于安全库存；
- 库存缺口持续扩大；
- 库存快照停止更新；
- 同一产品在多个仓库同时出现风险。

#### 警报与通知

- 警报触发、持续、升级、抑制和自动恢复；
- 相同实体与规则的持续观测自动关联，避免重复创建；
- Web 警报列表、详情、证据和时间线；
- 消息中心以及飞书或钉钉即时通知；
- 投递失败重试、幂等和审计。

### 3.2 当前数据能够支持的粒度

| 数据域 | 当前主要时间字段 | 合理监测粒度 | 边界 |
|---|---|---|---|
| 工序产出 | `stat_date` | 日、班次（存在班次编码时） | 不支持秒级设备变化 |
| 质量检验 | `inspection_date` | 日、批次、产品、工序 | 检验数据通常晚于生产发生 |
| 设备停机 | `start_time`、`end_time` | 分钟、小时、日 | 当前记录主要是已结束停机 |
| 库存快照 | `snapshot_date` | 日、最新快照 | 无实时出入库流水时不能解释补货原因 |
| 工单 | 计划开始、结束时间 | 工单、日 | 需要结合产出数据计算实际进度 |
| 设备主数据 | 安装日期、状态 | 当前上下文 | 缺少 `updated_at` 时不能作为实时状态证据 |

### 3.3 第一版不纳入范围

- 不宣称实现秒级实时 IoT 监控；
- 不宣称自动证明设备故障根因；
- 不自动写入或控制 MES、QMS、EAM、WMS；
- 不让 LLM 直接判断是否触发异常；
- 不让记忆系统自动修改企业阈值、指标或规则；
- 不建设完整维修、质量或生产工单系统；
- 不提供人工确认、误报判定、责任人指派、行动跟踪、审批、人工关闭或业务验收；
- 不自动创建 Agent 调查，Agent 仅可在未来作为独立下游订阅者接入；
- 不把周报、PDF、班次交接或处置流程作为监控 MVP 的依赖；
- 不在 LangGraph checkpoint 中保存完整业务数据；
- 不把未发布模型用于生产告警。

## 4. 设计原则

1. **语义稳定、物理可替换**：规则引用指标和业务维度，不引用固定表名和字段名。
2. **数据异常先于业务异常**：数据不可信时只创建数据质量事件，不创建误导性的生产事件。
3. **确定性监控、自动警报**：规则与统计方法决定是否触发、持续、升级和恢复，不由 LLM 决策。
4. **业务库只读**：所有业务查询通过现有只读网关、白名单、超时和成本门禁。
5. **状态可恢复**：扫描、评估、警报和投递均持久化，支持租约、幂等、重试和重启恢复。
6. **警报事实唯一**：警报事件是监控模块的事实源，Web 与外部消息只是其下游投影。
7. **职责单一**：监控模块只负责发现和通知，不承担调查、处置、人工验收或工单闭环。
8. **全链路可追溯**：指标版本、规则版本、数据范围、查询、评估结果、状态变化和投递结果全部留痕。

## 5. 当前项目能力评估

### 5.1 当前已有架构

ForgeSight 当前已经形成以下基础：

- MySQL/PostgreSQL 业务数据源与元数据扫描；
- PostgreSQL 平台数据库；
- 表、字段、关系、指标和数据源物理绑定；
- 只读 SQL 校验、查询超时、最大行数和 EXPLAIN 成本门禁；
- LangGraph 分析链路、持久化 Run、Step、Event、Artifact 和 checkpoint；
- 受治理的记忆系统、分析技能和建模系统；
- PostgreSQL 持久化任务、租约、重试和幂等模式；
- 消息中心、公告、周报、PDF/Excel 和邮件投递；
- 飞书、钉钉账号绑定、对话机器人和 PDF 投递；
- 用户、组织、数据范围和审计；
- 今日工作台、分析中心、调查记录、建模、报告和管理页面。

### 5.2 可以直接复用的能力

| 现有模块 | 复用内容 | 监控侧使用方式 |
|---|---|---|
| `metadata` | 数据源、表、字段、关系、扫描状态 | 确定规则可使用的物理资源和业务时间字段 |
| `knowledge` | 指标、业务定义、同义词、维度、数据源绑定 | 规则引用已发布指标，并按数据源编译查询 |
| `gateway` | 白名单、只读校验、方言检查、执行、超时、成本门禁、审计 | 所有监控取数统一通过受控执行边界 |
| `retrieval` | 关键词与向量混合检索、数据源隔离 | 辅助新数据源语义映射候选；不参与触发判断 |
| `modeling` | 异常检测算法、训练、评估、发布和推理审计 | 后期作为统计规则之外的可选检测器 |
| `messages` | 接收人展开、优先级、已读状态、Outbox | 新增警报触发、升级和恢复消息类型 |
| `delivery` | Provider、租约、重试、幂等和失败记录 | 复用飞书/钉钉发送基础，不复用 PDF 专属契约 |
| `audit` | 敏感动作审计 | 记录规则治理、监控查询、警报状态和投递结果 |
| `auth` | 用户、组织、角色和数据范围 | 决定警报可见范围和渠道接收人 |
| 前端图表与布局 | 趋势、排行、状态标签、详情 | 建设警报列表、趋势基线和证据页面 |

### 5.3 需要扩展但不应重写的能力

#### 消息中心

当前核心类型是周报与管理员公告。需要增加警报触发、持续提醒、升级和恢复类型，以及“查看警报”操作。

#### 外部投递

当前 `ReportDelivery` 强依赖报告版本和 PDF。即时警报通知应使用新的通用通知投递契约；可以复用飞书、钉钉 Provider、身份绑定、重试和幂等实现。

#### 数据权限

现有外部 IM 主要按 `analysis` 和 `weekly_report` 权限解析数据源。需要增加 `anomaly_monitoring` 业务权限，并进一步支持产线、车间、产品等维度范围。

#### 指标发布

现有逻辑会校验已登记表、字段和物理绑定，但正式监控依赖真正的公式解析、编译和回放验证。指标发布必须调用统一公式编译器，而不能仅检查表达式非空。

#### 可选下游扩展

Agent、记忆、技能、建模、周报和 PDF 能力可以在未来订阅已持久化的警报领域事件，但不得成为 Monitoring Worker 的同步依赖，也不计入监控模块的 MVP、状态机或交付完成定义。监控模块不会因这些下游不可用而停止检测和通知。

### 5.4 不应直接复用的内容

| 现有内容 | 不直接复用原因 | 正确处理 |
|---|---|---|
| `/operations/metrics` 平台告警 | 监控 Agent、Outbox、报告和投递健康，不是制造业务警报 | 保持为平台运维监控，业务监控新建独立领域 |
| 报告 `Anomaly` 结构 | 是报告版本快照，没有实时状态和去重 | 新建 `MonitoringAlert` 作为监控事实 |
| 报告 `Action` 结构 | 属于处置与验收领域 | 监控模块不创建行动模型 |
| Agent 自由 SQL | 监控需要稳定、低成本、可回放 | 使用规则编译出的查询计划，不让 LLM生成检测 SQL |
| 建模推理作为第一门禁 | 模型可能失效、漂移或不可解释 | 先硬规则和统计基线，模型只做受治理增强 |
| API 内 daemon thread | 多类任务耦合，进程退出会停止执行 | 复用租约逻辑，但生产部署拆成独立 Worker |

### 5.5 开源与主流方案的参考边界

本方案与 StarTree ThirdEye 的“指标异常和维度下钻”较为接近，但 ForgeSight 从企业数据底座和受治理业务语义出发，不以 Pinot 或实时指标平台为前提。调查、反馈和复盘能力仅作为架构参考，不纳入监控模块。建议借鉴设计而不是整体引入重型系统。

| 方案 | 借鉴内容 | 采用边界 |
|---|---|---|
| StarTree ThirdEye | 指标异常、维度下钻和告警降噪 | 主要架构参考，不引入其调查闭环或 Java/Pinot 技术栈 |
| Grafana Alerting | Pending/Firing、No Data、Error 和规则健康状态 | 借鉴状态分层，不把制造指标变成可观测性指标 |
| Prometheus/Alertmanager | `for`、持续告警、分组、静默、抑制和路由 | 借鉴降噪，不引入 Prometheus 时序存储作为前置条件 |
| Great Expectations/DataHub Assertions | 新鲜度、数据量、字段、Schema 和 SQL 断言 | 借鉴数据质量分类，不整体部署新的治理平台 |
| MetricFlow/Cube | 指标、维度、时间、Join、查询计划和预聚合 | 借鉴语义编译模型，避免与现有知识库重复建设 |
| Apache Superset Alerts | 独立调度、Worker、SQL 条件和消息投递 | 证明异步调度模式，不额外引入 Celery/Redis |
| OpenSearch Anomaly Detection | 在线时序、高基数实体和历史回放 | 后期算法参考，当前不引入 OpenSearch |
| Temporal | 持久化流程、重试和失败恢复 | 当前继续使用 PostgreSQL 租约与 Outbox |

候选轻量依赖应在编码前单独完成许可证、维护状态、Python 版本、部署体积和现有依赖重叠评估。本文不把任何新增库视为已批准依赖。

## 7. 新数据源适配流程

### 7.1 基本原则

系统固定的是规则类型、安全边界和业务语义，不固定数据库表名和字段名。

```text
通用规则模板 → 企业指标口径 → 数据源物理绑定 → 可执行监控计划
```

### 7.2 端到端流程

1. 创建只读数据源连接；
2. 扫描表、字段、关系、样例值和最大业务时间；
3. 识别生产、质量、设备、库存等业务对象候选；
4. 识别时间、实体、度量、状态和枚举字段候选；
5. 对已有指标生成数据源物理绑定候选；
6. 管理员确认字段语义、关联路径、单位和过滤条件；
7. 指标公式编译为目标数据库查询计划；
8. 执行小范围样例验证和历史覆盖检查；
9. 管理员审核并发布指标绑定；
10. 系统找出适用于该数据源的规则模板；
11. 自动创建监控规则实例草稿；
12. 规则执行历史回放，展示触发频率和数据质量；
13. 管理员发布规则；
14. 调度器开始生成持久化监控任务。

### 7.3 物理绑定示例

通用指标：

```text
产量 = SUM(合格数量 + 不良数量)
```

数据源 A：

```text
表：mes_process_output
表达式：SUM(good_qty + defect_qty)
时间：stat_date
产线：line_id
```

数据源 B：

```text
表：production_daily
表达式：SUM(actual_output)
时间：business_date
产线：production_line_code
```

规则始终引用“产量、生产日期、产线”，不会直接引用上述物理字段。

### 7.4 数据读取契约

仅使用“水位线减回看窗口”不能覆盖历史修改、整表覆盖和快照修订。每张参与监控的事实表必须发布独立读取契约：

```text
ingestionMode:
append | upsert | snapshot | full_replace

businessTimeField
updatedAtField
primaryKey
allowedLateness
lookbackWindow
reconciliationSchedule
deleteDetectionPolicy
```

各模式含义如下：

- `append`：新增记录为主，允许在迟到窗口内补录；
- `upsert`：历史主键对应记录可能更新，优先使用 `updatedAtField`；
- `snapshot`：同一业务日期的快照可能多次修订，只保留规则规定的有效版本；
- `full_replace`：整表或整个分区会被覆盖，不能依赖递增主键。

没有 `updated_at` 的数据源必须配置低频历史对账，例如每日回看最近 7 天、每周回看最近 90 天。删除记录无法通过普通水位线发现时，应使用分区行数、主键摘要或源系统提供的变更日志进行对账；无法可靠识别删除时必须在数据质量中披露。

## 8. 指标公式编译与发布门禁

### 8.1 编译技术路线

公式编译采用两层模型：

```text
受限业务指标 DSL
        ↓
ForgeSight 结构化指标 AST
        ↓
SQL AST/方言生成与现有安全网关
```

业务 DSL 第一版只允许：

- `sum`、`count`、`avg`、`min`、`max`；
- 加、减、乘、除和安全除法；
- 比例、条件过滤和指标引用；
- 已登记时间粒度和合法维度；
- 显式空值、分母为零和单位换算策略。

不从零开发完整 SQL 语法解析器。可评估 SQLGlot 等成熟 SQL AST 工具负责方言生成和结构校验，但引入前必须验证许可证、Python 版本、维护状态、包体积以及与现有 SQL 校验器的职责边界。无论是否采用第三方库，表字段白名单、只读校验、EXPLAIN 成本门禁和审计仍由 ForgeSight 负责。

### 8.2 编译输入

- 指标语义公式；
- 数据源类型；
- 物理表与字段映射；
- 过滤表达式；
- 默认时间字段；
- 允许分组维度；
- 表关联路径；
- 单位换算。

### 8.3 编译输出

- 结构化公式 AST；
- 使用的表、字段和关联；
- 目标方言 SQL 片段；
- 必需分母和空值策略；
- 可用时间与分组维度；
- 编译版本和校验摘要。

### 8.4 发布硬门禁

- 所有表和字段已经登记；
- 关联路径没有歧义；
- 聚合层级合法，避免先 `LIMIT` 后聚合；
- 时间字段存在且类型有效；
- 表达式只能使用允许函数；
- 生成 SQL 只读；
- 数据库方言兼容；
- EXPLAIN 成本通过；
- 样例查询返回合理结构；
- 当前数据源存在有效时间覆盖；
- 物理绑定和指标版本冻结；
- 管理员审核通过。

## 9. 监控规则设计

### 9.1 规则组成

每条规则至少包括：

- 规则模板和版本；
- 数据源；
- 指标和指标绑定版本；
- 实体维度；
- 时间维度与粒度；
- 过滤维度；
- 基线方法；
- 触发条件；
- 最小样本量；
- 连续周期；
- 恢复条件；
- 冷却和抑制策略；
- 严重度计算；
- 通知范围与接收人策略；
- 启停状态和生效时间。

规则中的触发与恢复参数必须显式保存：

- `pending_periods`：连续满足多少次后从 pending 进入 firing；
- `open_threshold`：开启异常的阈值；
- `close_threshold`：恢复阈值，用于形成迟滞，避免边界抖动；
- `keep_firing_periods`：短暂恢复后继续保持 firing 的周期数；
- `mute_window`：维护、停产、节假日或已知业务窗口；
- `group_key`：可合并为一个通知或共同原因事件的键；
- `inhibit_by`：上游事件对下游规则的抑制关系；
- `notification_interval`：持续事件的重复提醒间隔。

### 9.2 规则来源优先级

1. 企业明确阈值和计划目标；
2. 已发布指标口径；
3. 同一对象历史基线；
4. 同类对象基线；
5. 已发布统计或机器学习模型；
6. 管理员基于业务反馈创建并审核的规则草稿。

硬业务规则优先于统计基线，统计基线优先于模型。所有规则都必须由有权限的管理员审核发布。

### 9.3 第一批规则模板

| 模板 | 指标 | 典型粒度 | 核心判断 |
|---|---|---|---|
| 数据断流 | 最大业务时间 | 小时/日 | 超过允许延迟仍未推进 |
| 产线产量下降 | 产量 | 日/班次/产线 | 相对计划或历史基线下降 |
| 工序良率下降 | 工序良率 | 日/班次/工序 | 低于红线或控制下限 |
| 抽检不良率上升 | 抽检不良率 | 日/产品/工序 | 高于红线或历史上限 |
| 非计划停机 | 非计划停机时长 | 分钟/小时/日/设备 | 单次过长、累计过高或复发 |
| 安全库存不足 | 可用库存与安全库存 | 最新快照/产品/仓库 | 可用量低于安全量且持续 |
| 工单进度风险 | 产量进度与时间进度 | 工单/日 | 时间进度显著领先产量进度 |

### 9.4 规则示例

```json
{
  "templateCode": "production-output-drop",
  "metricId": "M-001",
  "entityDimension": "生产线",
  "timeDimension": "生产日期",
  "grain": "day",
  "baseline": {"method": "median", "window": 14},
  "condition": {
    "operator": "drop_rate_gte",
    "openThreshold": 0.2,
    "closeThreshold": 0.1
  },
  "minimumSamples": 3,
  "pendingPeriods": 2,
  "keepFiringPeriods": 1,
  "recoveryPeriods": 2,
  "notificationIntervalMinutes": 240,
  "muteWindows": [],
  "inhibitBy": ["source-data-stale"]
}
```

### 9.5 告警降噪与抑制

规则执行必须按以下顺序处理：

1. 判断当前是否处于维护或停产静默窗口；
2. 检查上游数据质量事件是否抑制本规则；
3. 按 `group_key` 批量计算相关实体；
4. 满足开启阈值后先进入 pending；
5. 连续达到 `pending_periods` 才进入 firing；
6. 低于开启阈值但未达到关闭阈值时保持原状态；
7. 达到关闭阈值后继续观察 `keep_firing_periods` 和恢复周期；
8. 只在首次触发、严重度升级、恢复或通知间隔到期时发送消息。

典型抑制关系为：

```text
数据源断流 firing
→ 抑制该数据源的产量下降、良率下降和库存突变通知
→ 保留规则执行结果为 no_data 或 inhibited
```

### 9.6 规则生命周期

```text
draft → validating → reviewing → published → paused → retired
```

任何影响公式、维度、阈值、基线或严重度的修改都生成新版本。历史警报继续引用触发时的旧版本。

## 10. 数据模型

### 10.1 `MonitoringRuleTemplate`

保存可跨数据源复用的语义规则模板：

- `id`、`code`、`name`、`topic`；
- `metric_id`；
- `entity_dimension`、`time_dimension`、`grain`；
- `baseline_json`、`condition_json`；
- `quality_gate_json`、`severity_policy_json`；
- `recovery_policy_json`、`notification_policy_json`；
- `version`、`status`、审核和发布时间。

### 10.2 `MonitoringRule`

保存模板针对某个数据源的执行实例：

- `template_id`、`template_version`；
- `source_id`；
- `metric_id`、`metric_binding_id`、绑定版本；
- 实体、时间和过滤维度绑定；
- 编译计划与校验摘要；
- 调度周期；
- 生效范围；
- 状态、版本和审核记录。

### 10.3 `MonitoringCursor`

保存增量读取水位线：

- `source_id`、`rule_id`；
- `last_business_time`；
- `last_primary_key`；
- `last_success_at`；
- `last_source_update_at`；
- `lookback_seconds`；
- `cursor_version`。

### 10.4 `MonitoringTask`

保存持久化调度任务：

- 规则、计划执行时间和查询窗口；
- `queued/running/retry_wait/succeeded/failed/dead_letter`；
- 幂等键；
- 尝试次数和最大次数；
- 租约所有者和到期时间；
- 错误、安全检查和执行摘要；
- 创建、开始和完成时间。

### 10.5 `MonitoringObservation`

保存规则计算形成的可复查观测值：

- 指标、实体和逻辑周期；
- 当前值、基线、上下界和偏差；
- 样本量、覆盖率和数据截止时间；
- 指标/绑定/规则版本；
- 查询 Artifact 和校验 Artifact；
- 数据质量状态；
- `evaluation_state`：`normal/pending/firing/no_data/error/inhibited/muted`；
- 观测幂等键和计算修订号。

观测值应是聚合结果，不保存完整业务明细。

### 10.6 `MonitoringAlert`

保存实时警报事实：

- 类型、主题、严重度；
- 数据源、规则、指标和版本；
- 实体类型、实体 ID 和显示名；
- 开始时间、首次发现和最近出现；
- 当前值、基线、偏差、单位和样本量；
- 数据截止时间和质量状态；
- 不含逻辑周期的事件关联键；
- `firing/recovering/resolved` 状态和优先级；
- 首次通知、最近通知和自动恢复时间；
- 恢复和复发关联关系。

### 10.7 `AlertEvidence`

保存：

- 证据类型；
- Observation、查询 Artifact 或模型推理引用；
- 冻结摘要；
- 校验状态和置信度；
- 创建时间。

### 10.8 `AlertDelivery`

保存每次 Web 之外的外部投递：

- `alert_id`、消息类型和接收范围；
- 渠道、目标账号或群标识；
- `queued/sending/sent/retry_wait/failed`；
- 幂等键、尝试次数、租约和错误摘要；
- 服务商消息 ID、首次发送和完成时间。

监控领域不创建 `AnomalyAction` 或 `AnomalyFeedback`。若未来建设独立处置系统，应通过领域事件订阅 `MonitoringAlert`，并维护自己的状态和权限。

### 10.9 `MonitoringSourceContract`

保存表级读取契约并版本化：

- 数据源和物理表；
- `ingestion_mode`；
- 业务时间、更新时间和主键字段；
- 允许迟到时间和回看窗口；
- 历史对账周期；
- 删除检测策略；
- 当前版本、状态、审核和发布时间。

规则执行时冻结读取契约版本，避免表的同步方式改变后历史观测无法解释。

## 11. 调度、读取和任务可靠性

### 11.1 任务生成

调度器根据已发布规则的执行周期创建 `MonitoringTask`。幂等键建议为：

```text
ruleId + ruleVersion + logicalWindowStart + logicalWindowEnd
```

### 11.2 任务认领

Monitoring Worker 使用 PostgreSQL 行锁和 `SKIP LOCKED` 原子认领任务，写入租约。租约过期后允许其他 Worker 重新认领；超过最大次数进入 dead letter。

### 11.3 增量读取

查询范围采用：

```text
上次水位线 - 回看窗口 → 当前安全截止时间
```

回看窗口用于处理延迟到达和补录数据，最终通过逻辑周期和观测幂等键去重。具体读取策略必须服从第 7.4 节的数据读取契约；`upsert`、`snapshot` 和 `full_replace` 不能只依赖业务时间水位线。

### 11.4 历史对账

Monitoring Worker 除高频增量任务外，还要生成低频 `reconciliation` 任务：

- 按读取契约重新计算历史窗口；
- 比较 Observation 的数据摘要、样本量和聚合值；
- 发现历史修订时生成新观测修订，不覆盖旧证据；
- 重新评估受影响事件，但已经完成人工处置的事件不得静默改写；
- 将“历史数据修订导致状态变化”作为独立时间线事件和审计记录。

### 11.5 批量聚合与查询预算

不能为每条产线、产品、工序或设备分别发送一条 SQL。每条规则每个窗口原则上只生成一条批量聚合查询，在数据库中按实体分组，再由 Worker 批量计算规则：

```text
一个规则窗口
→ 一条受控聚合 SQL
→ GROUP BY 合法实体维度
→ 批量 Observation
→ 批量状态评估
```

每条规则需要设置：

- 最大实体数量；
- 最大维度组合数量；
- 最大回看范围；
- 预计扫描行数和查询成本预算；
- 单数据源并发数；
- Top-N 或业务实体白名单；
- 超限时的分批、降级或阻断策略。

高频或高成本规则应优先使用数据库侧预聚合视图、平台聚合缓存或离线汇总结果。预聚合只保存必要的指标、实体、周期和质量摘要，不复制无关业务明细。

### 11.6 进程隔离

监控模块生产部署至少拆分：

- FastAPI API；
- Monitoring Worker；
- Delivery Worker。

开发环境可以在同一进程启动，但不能把 daemon thread 作为生产可靠性的唯一保证。

## 12. 数据质量门禁

### 12.1 新鲜度

- 数据源连接状态；
- 表最大业务时间；
- 与预期更新频率的差值；
- 当前周期是否完整；
- 数据是否连续推进。

### 12.2 完整性

- 最小样本量；
- 主键重复；
- 关键字段缺失；
- 分母为零；
- 数值范围异常；
- 枚举漂移；
- 时间倒序；
- 分组覆盖突变。

### 12.3 数据异常与业务异常分流

```text
数据质量失败 → 创建 data_quality 事件 → 停止业务异常判断
数据质量通过 → 执行业务规则
```

数据事件必须明确显示缺失、延迟、样本和截止时间，避免业务人员将坏数据误判为生产问题。

## 13. 异常检测器

### 13.1 硬业务规则

适用于安全库存、质量红线、计划偏差和非计划停机等明确规则。

### 13.2 统计基线

第一版只实现可解释、容易回放验证的算法：

- 中位数与 MAD；
- 同星期和同班次比较；
- Shewhart 控制界限；
- 最小样本量；
- 连续周期与迟滞恢复。

基线计算必须排除不完整周期，并保存基线窗口和计算版本。

后续在数据覆盖、季节性和回放评估成熟后再增加：

- 均值、标准差和历史分位数；
- EWMA 与 CUSUM；
- 预测区间和变点检测；
- Isolation Forest 与 RCF 等模型方法。

### 13.3 计划进度

工单进度风险建议采用：

```text
时间进度 = 已经过计划时间 / 工单计划总时间
产量进度 = 当前累计产量 / 计划数量
进度差 = 时间进度 - 产量进度
```

需要配置生产日历、停工时间和班次，否则必须披露限制。

### 13.4 已发布模型

模型只作为可选检测器，必须满足：

- 模型状态为 `published`；
- 数据源、特征和实体范围一致；
- 模型版本、阈值和输入留痕；
- 数据质量门禁先通过；
- 推理失败自动退化为规则检测；
- 模型输出不绕过人工处置权限。

## 14. 警报去重、分级和生命周期

### 14.1 事件关联键与观测幂等键

```text
事件关联键：
sourceId + ruleVersion + metricId + entityType + entityId

观测幂等键：
ruleId + ruleVersion + entityId + logicalPeriod
```

`logicalPeriod` 只属于观测幂等键，不能进入持续警报的事件关联键。一个持续警报关联多条周期 Observation：

```text
MonitoringAlert: L03 工序良率持续下降
├── Observation: 8月24日
├── Observation: 8月25日
└── Observation: 8月26日
```

同一警报持续 firing 时更新当前值、最近出现时间、严重度和连续周期，不创建新警报。警报自动 resolved 后，在配置的复发关联窗口内再次触发时恢复为 firing 并增加复发计数；超过窗口则创建新警报并保留历史关联。

### 14.2 严重度

建议统一为：

- `critical`：安全、重大质量或大范围停线风险；
- `high`：明显影响计划、质量、设备或库存；
- `medium`：需要关注但尚未造成重大影响；
- `low`：轻微变化或观察项。

严重度由确定性策略计算，综合偏差幅度、持续时间、影响范围、业务优先级和数据可信度。

### 14.3 分层状态机

规则评估、警报事实和消息投递必须使用三套互相引用但不混合的状态。

#### 规则评估状态 `EvaluationState`

```text
normal → pending → firing

独立结果：no_data / error / inhibited / muted
```

- `normal`：本周期未达到开启条件；
- `pending`：达到开启阈值，但连续周期不足；
- `firing`：达到正式触发条件；
- `no_data`：没有足够数据；
- `error`：查询、编译或计算失败；
- `inhibited`：被上游事件抑制；
- `muted`：处于维护或停产窗口。

`no_data` 和 `error` 不等同于 normal，必须单独暴露规则执行健康度。

#### 警报状态 `AlertState`

```text
firing → recovering → resolved
   ▲          │
   └──────────┘（恢复条件失效）
```

- `firing`：已经达到触发条件并处于告警中；
- `recovering`：达到恢复阈值，但尚未满足连续恢复周期；
- `resolved`：连续满足恢复策略，系统自动恢复。

不存在 `acknowledged`、`investigating`、`action_pending`、`false_positive` 或人工 `closed` 状态。数据质量不足不创建业务警报，而是生成独立数据质量警报，并使依赖它的业务规则进入 `no_data` 或 `inhibited`。

#### 投递状态 `DeliveryState`

```text
queued → sending → sent
                 → retry_wait → sending
                 → failed
```

发送失败不改变警报状态，警报自动恢复也不覆盖历史投递结果。

### 14.4 恢复与复发

恢复必须由明确策略判断，例如连续两个完整周期回到基线 90% 以上。一次暂时回落只进入 `recovering`，不能直接标记为 `resolved`。

已 `resolved` 警报在复发关联窗口内再次触发时恢复为 `firing` 并记录复发次数；超过窗口时创建新警报并关联历史记录。全过程由规则自动驱动，不依赖人工验收或关闭。

## 15. 可选下游扩展（不属于监控模块）

监控模块在同一事务内写入警报状态和 `DomainEventOutbox`，可发布 `alert.firing`、`alert.severity_changed`、`alert.reminder_due` 和 `alert.resolved` 事件。未来的 Agent 调查、周报、班次交接、工单或处置系统可以独立订阅，但必须满足：

- 下游失败不阻断 Monitoring Worker、警报状态或即时通知；
- 下游维护独立任务和状态，不向 `AlertState` 增加人工处置状态；
- 下游只能读取调用方有权查看的警报与证据；
- 监控模块不自动创建 Agent Run、行动、审批或验收记录；
- 下游输出不能反向覆盖已发布规则和历史观测。

普通分析链路、记忆和技能系统保持不变。用户若从警报详情主动发起普通分析，该行为属于分析模块，不属于监控 MVP。

## 16. 建模能力复用

建模不作为第一阶段依赖。后续可作为受治理的检测器，用于：

- 无监督异常评分；
- 质量风险分类；
- 产量预测和预测区间；
- 停机风险排序；
- 动态阈值建议。

调用模型前必须确认：

- 当前数据源、实体、字段和时间范围与训练契约一致；
- 模型已发布且未下线；
- 输入数据质量通过；
- 推理结果记录模型版本和阈值；
- 模型失败时规则链路继续可用。

## 17. 明确排除：业务处置与验收

本模块到“警报已送达或自动恢复”为止，不参与后续业务处置。以下能力明确不建模、不提供 API、不出现在警报状态机中：

- 人工确认收到、误报判定和责任人指派；
- 原因调查、Agent 调查和现场事实补充；
- 行动计划、审批、执行反馈和逾期管理；
- MES、QMS、EAM、WMS 工单写入；
- 人工验收、人工关闭和接班确认。

若未来确有需要，应建设独立“事件处置”领域，通过 Outbox 订阅警报事实。该领域的权限、状态、审计和交付标准与监控模块分离。

## 18. 消息中心与飞书/钉钉

### 18.1 新消息类型

- `monitoring_alert_firing`；
- `monitoring_alert_escalated`；
- `monitoring_alert_reminder`；
- `monitoring_alert_resolved`；
- `monitoring_data_issue`。

### 18.2 即时卡片内容

- 异常标题和严重度；
- 实体、指标和当前值；
- 基线、偏差和持续时间；
- 样本量和数据截止时间；
- 规则名称、数据质量状态和数据源；

## 19. 可选报告订阅边界

监控 MVP 不生成周报、PDF 或交接记录。未来报告模块若订阅警报事件，应只读取周期内已持久化的 `MonitoringAlert` 快照，而不能重新让 LLM 判断异常或改变警报状态。可选摘要包括：

- 新增、持续和升级警报；
- 当前 firing 警报；
- 自动恢复警报；
- 复发警报；
- 数据质量问题；
- 平均持续时间和自动恢复时间。

报告投递失败不得影响监控任务、警报状态或即时通知；报告能力不计入本模块完成定义。

## 23. 可观测性与运行指标

制造监控自身需要独立运维指标：

- 已发布规则数；
- 到期、排队、运行、重试和 dead-letter 任务数；
- 数据源扫描延迟；
- 每类规则执行成功率和 P95 时长；
- 单数据源查询次数、扫描行数和成本门禁命中；
- 警报创建、去重、升级、恢复和复发数量；

这些指标属于监控模块的运行质量，可汇总进入现有管理员运维页面，但不能与制造业务异常混为同一事件类型。

## 27. 第一版最小可交付范围

为了控制比赛和首轮真实验证风险，第一版只完成一条可端到端演示的“监控—警报—通知—自动恢复”纵向链路：

1. 一个数据源；
2. 三类规则：数据断流、工序良率下降、非计划停机；
3. 日级定时监测，停机记录按当前数据可用粒度处理；
4. 企业硬阈值、中位数/MAD、同星期或同班次比较和 Shewhart 控制界限；
5. `normal/pending/firing/no_data/error` 规则评估；
6. 警报关联、观测幂等、持续更新、升级、自动恢复和复发关联；
7. 连续周期、开启/关闭迟滞、短暂恢复保持、静默和数据断流抑制；
8. Web 警报列表、详情与证据；
9. 飞书或钉钉先完成一个即时警报渠道，覆盖触发、升级和恢复；
10. 完整权限、审计、查询预算、重试和重启恢复。

第二批再增加产量下降、安全库存、双平台同时投递和更细粒度调度。首期不实现 Agent 调查、周报/PDF、人工确认与关闭、行动验收、模型检测、外部工单写入、IoT 流接入、复杂流程编排、OpenSearch、Temporal 或 Celery/Redis。

## 28. 软件交付验收场景

以下“验收”指开发和测试验收，不是对制造异常的业务处置验收。

### 场景一：工序良率下降（首期核心）

PR06 连续两个完整生产日工序良率低于企业红线或历史 MAD 下界。系统创建高等级警报，展示当前值、基线、样本、数据截止时间和主要产品，并向质量主管投递。新数据连续两个周期达到恢复阈值后，系统自动标记 `resolved` 并发送恢复通知，全程不需要人工确认或关闭。

### 场景二：非计划停机（首期核心）

E0009 单次或累计非计划停机超过企业阈值。系统创建警报并显示停机时长、历史同类停机、受影响产线和同期产量证据，同时向设备主管投递。数据达到恢复条件后自动恢复，不创建 Agent Run 或外部 EAM 工单。

### 场景三：数据断流

产出表超过预期更新时间仍未推进。系统只创建数据质量警报，不创建产量下降警报；数据恢复后自动解除断流，再继续业务检测。

### 场景四：新数据源

第二个数据源使用不同表字段。管理员完成一次语义映射和指标绑定后，同一产量下降规则模板成功实例化，无须修改检测代码。

### 场景五：权限隔离

L03 警报只对具备对应数据范围的生产主管可见并投递。其他用户即使绑定飞书或钉钉，也不能收到或打开详情。

### 场景六：产量下降（第二批模板）

L03 连续两个完整生产日产量低于过去 14 个生产日中位数 20%。系统将多个周期观测关联到同一个持续警报，而不是每天创建新警报。当前周期短暂恢复但未满足连续恢复条件时保持 `recovering` 或回到 `firing`。

## 29. 主要风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| 新数据源字段语义不清 | 规则无法迁移或口径错误 | 候选映射、样例验证和人工发布 |
| 当前周期未完整 | 大量产量误报 | 周期完整性和同进度比较 |
| 数据延迟、历史修改或补录 | 重复或遗漏警报 | 表级读取契约、水位线回看、历史对账、观测幂等和警报关联 |
| 查询成本或高维实体爆炸 | 影响生产数据库 | 批量 GROUP BY、实体/维度上限、预聚合、EXPLAIN 门禁和并发预算 |
| 阈值不合适 | 警报过多或漏报 | 历史回放、连续周期、迟滞、冷却、抑制和版本治理 |
| 权限配置错误 | 数据泄漏 | 发送与读取时双重鉴权，维度范围和审计 |
| Worker 与 API 耦合 | 重启中断 | 独立 Worker、租约和持久化队列 |
| 模型漂移 | 错误异常评分 | 模型治理、版本绑定、监控和规则降级 |

## 30. 关键架构决策

1. 新建独立 `monitoring` 领域，不把监控逻辑放入 `agent`、`modeling` 或 `reports`。
2. `MonitoringAlert` 是事实源，Web 与即时消息都是其下游投影。
3. 规则保存语义引用和结构化条件，不保存任意自由 SQL。
4. 新数据源通过指标和维度物理绑定适配，不复制规则代码。
5. 数据质量失败时禁止继续产生业务警报。
6. Agent、记忆、技能和报告均不是监控链路依赖，只能作为可选下游订阅者。
7. 即时警报通知不复用 PDF 专属投递记录，但复用渠道 Provider 和可靠任务模式。
8. 生产部署使用独立 Worker，数据库租约是恢复依据。
9. 监控领域不保存行动、人工反馈、验收或外部工单状态。
10. 第一版以确定性规则为主，建模能力在治理成熟后增强。
11. 持续警报和周期观测使用不同的唯一键，`logicalPeriod` 不进入警报关联键。
12. Evaluation、Alert 和 Delivery 状态分离，No Data/Error 不伪装成正常。
13. 每张监控表必须声明读取模式，并通过低频历史对账补偿水位线盲区。
14. 每条规则按窗口执行批量聚合，禁止按单个实体产生 N 条查询。
15. 指标采用受限业务 DSL 和结构化 AST；SQL AST 工具仅作为待评估实现选项。

16. 警报只能由规则评估自动进入 firing、recovering 和 resolved，不设置人工确认或关闭入口。

## 31. 完成定义

“智能异常监控与警报”完成不能只以页面或单次告警为标准，必须同时满足：

- 新数据源通过语义绑定复用规则，不依赖固定表字段；
- 数据质量警报和业务警报正确分流；
- 任务在重启、超时和并发条件下不丢失、不重复；
- 警报具备稳定状态、证据、严重度和审计；
- Web 与至少一个 IM 渠道引用同一个警报事实；
- 持续观测不重复建警报，满足策略后能够自动恢复；
- Agent、记忆、周报或处置系统不可用时监控与通知仍可运行；
- 系统不存在人工确认、指派、行动、验收或关闭对监控状态的依赖；
- 第二个不同物理结构的数据源通过软件交付测试；
- 所有硬门禁、权限、降级和失败恢复均有自动化测试。

满足以上条件后，ForgeSight 才从被动问数系统升级为可用于真实制造场景的主动异常监控与警报平台。
